# M13 — Controlled Explicit Memory Save Routing

> Status: pre-implementation contract; no M13 code, migration, test, or E2E result exists yet.
> Baseline: `main@199d9dffdb2d4c69e210ffc0ad6c3c8aed6d9b2d`.
> Existing boundaries: [M1 explicit save](13-First-Vertical-Slice.md), [M4 idempotency](19-Fourth-Vertical-Slice.md), [M5 read-only triage](21-Fifth-Vertical-Slice.md), [M11 read-only routing](34-Eleventh-Vertical-Slice.md), [M12 routing audit](37-Twelfth-Vertical-Slice.md), and [Runtime state](../02-Architecture/Runtime/State.md).

## Goal and exact scope

Connect the already implemented `save_memory()` to the existing `POST /requests/route` boundary for **one explicitly supplied user-scope Memory**. The routing model proposes only `memory.save` or `no_action`; NOAH validates and, at most once, invokes the existing internal Python function. M1/M4 remain the owners of Memory, Task, Execution, and the write-key mapping. M12's separate operational audit records the router decision and verified correlation. This does not introduce another Memory writer, a parent Task, a generic dispatcher, or automatic recovery.

The current M11/M12 route is read-only. This document defines a future, additive M13 branch; it does not describe `memory.save` routing as currently implemented or revise the historical M11/M12 validation results. The existing `POST /memories` contract and routes without `memory_save` remain unchanged.

## API request and explicit authorization

Use the existing bearer-authenticated `POST /requests/route`. The only new request shape is exactly:

```json
{
  "question": "내가 명시한 내용을 내 메모로 저장해줘.",
  "memory_save": {
    "content": "공개 가능한 합성 테스트 메모"
  }
}
```

The caller also supplies **exactly one** `Idempotency-Key` header using M4's existing 1–128 character ASCII token syntax. Missing, empty, invalid, or duplicate headers are rejected before a routing audit reservation, model call, or `save_memory()` call. The key is never generated by the model or derived from `router_id`.

Use HTTP 401 `UNAUTHENTICATED` for a missing/revoked token; HTTP 400 `INVALID_REQUEST` for a malformed shape, duplicate JSON key, or forbidden target field; HTTP 400 `INVALID_CONTENT` for absent/invalid content; HTTP 400 `IDEMPOTENCY_KEY_REQUIRED` for a missing header; and M4's HTTP 400 `INVALID_IDEMPOTENCY_KEY` for an invalid or duplicate header. A prerequisite database failure uses HTTP 503 `DATABASE_UNAVAILABLE`. These are router preflight outcomes, not delegated M1 rejection records.

`memory_save` must be an object with exactly one string field, `content`. Empty or whitespace-only content and content exceeding M1's 10,000 Unicode-character limit are rejected. M1's existing trim-before-storage normalization remains authoritative. Unknown request or nested fields, duplicate JSON keys, `project_id`, caller-supplied scope or owner, and a model-supplied argument are rejected for this branch. The server derives `action="save_memory"`, `scope="user"`, and `owner_user_id` from the authenticated principal solely to form the existing `save_memory()` input. Project Memory is not eligible in M13.

**Only the caller's `memory_save.content` is the source of stored content.** `question` is for route selection only. NOAH must never extract, copy, summarize, rewrite, or fall back to `question` when constructing the Memory content. An absent `memory_save.content` cannot become a save by model choice. The presence of the explicit write object authorizes NOAH to consider this one write, but does not bypass authentication, validation, permission, or the final model-choice allowlist. A router question that does not clearly request the supplied write should yield `no_action`, not an inferred write. The model's `memory.save` proposal alone never grants permission.

Requests without `memory_save` keep M11/M12's exact input, read-only candidate set, project precheck, and behavior. An `Idempotency-Key` header on such a legacy request does not turn it into a write and does not create an M4 mapping.

## Preflight and model visibility

For an M13-shaped request, authenticate the token and validate the exact JSON shape, M11's 1–300 character / 512 UTF-8 byte routing question and 2,048 byte prompt bound, `memory_save.content`, the user-only target, and `Idempotency-Key` presence and format **before** reserving audit or calling the model. Retain M11's known-credential screening of the question in this preflight. A definite preflight rejection creates no routing audit, model call, delegated Memory write, Task, Execution, or write-key mapping.

After preflight passes, the routing audit reservation must be durably confirmed **before** checking the dedicated/local Ollama binding or routing model availability and before invoking the model. An unsafe or unavailable Ollama listener, unavailable routing model, invocation failure, timeout, or invalid model output is a model-stage failure inside the existing M12 routing audit boundary. Record it using M12's existing model/routing failure semantics when possible; do not call `save_memory()`. Memory, Task, Execution, and M4 write-key mapping deltas remain zero. This is neither a `memory.save` failure nor `WRITE_OUTCOME_UNKNOWN`, because the write delegate did not start. Do not automatically retry or fall back to another route.

The routing model receives the bounded `question`, fixed descriptions of `memory.save` and `no_action`, and a fixed `memory_save_present=true` marker indicating that NOAH has validated an explicit write payload. It receives no `memory_save.content`, owner UUID, project ID, OS path, database credential, API token, or idempotency key. This prevents automatic transfer of the separate content field; a caller who copies private content into `question` has explicitly made it part of the routing question, and this slice cannot retract text already sent to the verified local model.

For this branch, the model output remains a strict JSON object with exactly one `route` string:

```json
{
  "type": "object",
  "properties": {"route": {"type": "string", "enum": ["memory.save", "no_action"]}},
  "required": ["route"],
  "additionalProperties": false
}
```

A proposal of `memory.query`, `project.documents.answer.auto`, an unknown name, or an argument is malformed for this branch; it is not coerced to a write or silently dispatched elsewhere. `no_action` is a successful routing decision with no `save_memory()` call or Capability Task/Execution. The legacy read-only model schema is unchanged for requests without `memory_save`.

## One delegate and durable ownership

After a validated `memory.save` proposal, NOAH rechecks that the token still identifies the same actor **before** committing `route_validated`. A revocation or prerequisite DB failure at this point is a routing-stage denial: finalize the existing `reserved` audit as a safe routing failure when possible and invoke no delegate. NOAH then commits M12's `route_validated` and `dispatch_prepared` stages before invoking the delegate. A definite failure or lost commit acknowledgement in audit reservation or any pre-delegate stage stops the request **without calling `save_memory()`**. `dispatch_prepared` is only a recorded intention; it proves neither that the Python call began nor that any Memory was stored. No automatic retry or alternate Capability follows.

The existing `save_memory()` authenticates again at delegation and enforces its own user-scope write permission; a revocation between the router recheck and this call cannot be overridden by the router or model. NOAH constructs the M1 input only from the validated explicit content and server-derived authenticated user target, and passes the caller's unchanged key to **one internal `save_memory()` call**. No internal HTTP request is made.

`save_memory()` alone owns its current Task/Execution reservation, unique M4 mapping, Memory insertion, database readback, terminal commit, and safe failure result. The router creates no parent or duplicate Task, Execution, Memory, or Capability Evidence. M13 adds no Task/Execution status values. M5 continues to inspect `memory.save` records read-only; a routing audit stage is not recovery evidence and M5 does not repair routing audits.

## M4 key, explicit replay, and uncertain outcome

The canonical M4 fingerprint continues to cover the normalized content, `save_memory` action, user scope, and authenticated owner. The routing question is not stored as Memory and is not part of that write fingerprint. The same actor, key, and canonical write request **when it reaches `save_memory()` again** may return the original HTTP 200 `replayed=true` result and original Memory/Task/Execution IDs. A changed canonical write under the same key yields M4's HTTP 409 `IDEMPOTENCY_CONFLICT`; a still-running original yields HTTP 202 `pending`. Distinct keys may intentionally save identical content twice. A pre-delegate rejection or `no_action` creates no M4 reservation.

Each router request has its own server-issued `router_id`; multiple router audit rows may refer to the same M4 execution after an explicit replay. `router_id` is not a client idempotency ID and must not be used to deduplicate writes. Routing the same HTTP request again may produce a different model choice. M13 therefore **does not guarantee router-level replay** or automatically repeat a write. After an uncertain result or lost response, the caller must retain the original key and explicit content. The existing direct `POST /memories` endpoint with the same canonical body and key is an available explicit M4 outcome-check path; otherwise an operator may inspect M5's read-only report. Neither route infers success or failure from age or from the M12 audit alone.

Preserve M1/M4's returned status and body inside the existing M11 `result` envelope: first verified save HTTP 201, verified replay HTTP 200, pending HTTP 202, conflict HTTP 409, definite write failure with its original safe code, and `WRITE_OUTCOME_UNKNOWN` as uncertain. The router does not translate `pending` or `WRITE_OUTCOME_UNKNOWN` into success or a definite failure, and does not fall back to another Capability.

## M12 audit lifecycle and correlation

Keep one separate operational `noah.routing_audit` row per eligible M13 router request and the existing monotonic stages `reserved → route_validated → dispatch_prepared → observed`. Direct `observed` transitions remain available for a definite routing-model failure, invalid proposal, or `no_action`. The audit is not a Task, Execution, DDR-004 Capability Evidence, idempotency mapping, or source of truth for the write outcome. It has no transaction spanning Ollama or `save_memory()`.

The smallest additive schema change permits `memory.save` in the existing bounded `validated_route`, `delegate_capability`, and dispatch-prepared constraints. Keep the current audit constraint that a stored `delegate_execution_id` requires a `delegate_task_id`: M1 can record a rejected Execution **without** a Task, so the audit must leave both IDs null for that case and retain only a verified delegate request ID and safe outcome code. The unchanged M1 result body retains its own rejection Execution ID. This is deliberately limited correlation, not a fabricated parent Task or a claim that no rejection Execution exists. Do not add a hard FK between routing audit and M1/M4 rows. No new general audit/execution framework, write-result table, or audit payload column is required.

On a returned M1/M4 result with a Task, correlate only UUIDs verified against the existing Execution's request ID, authenticated actor, capability `memory.save`, and Task relationship. For a keyed replay, verify the existing actor/key mapping and normalized write fingerprint transiently; **do not store** the key, key digest, fingerprint, or content in the audit. A pre-Task rejection may correlate its request ID after checking the returned Execution/request relationship, but must not claim a Task, actor-bound execution ownership, or stored Execution ID when those cannot be established under the current audit constraint. Where returned IDs or database relationships cannot be verified, omit unverified correlation IDs, classify `correlation_unverified`, and preserve the original delegate response. A returned `WRITE_OUTCOME_UNKNOWN` or `pending` is an uncertain/nonterminal delegate observation, not `delegate_returned` success. A bare `dispatch_prepared` or missing terminal audit update cannot prove a write occurred.

Only bounded symbolic route, observation class, HTTP status, safe outcome/failure code, timestamps, and verified request/Task/Execution UUIDs may enter the audit. It must not store question, prompt, raw model output, Memory content, `Idempotency-Key` or its hash, token or token hash, DB password, generated answer, OS path, or local mapping path. M1's own Memory and M4's existing key digest/fingerprint storage remain under their separate established contracts.

After delegation, a definite failure or unknown acknowledgement of the final `observed` audit update sets `routing.audit_status=unconfirmed` but preserves the already obtained M1/M4 HTTP status, result body, and durable outcome. `recorded` means the terminal audit update is confirmed committed; it does not mean the write succeeded. `unconfirmed` means that audit confirmation is missing; it does not mean the delegate failed, was rolled back, or should be retried. M12's `no_action` final-audit-failure behavior remains a routing-stage HTTP 503 with no delegate. **Unknown Outcome != Failed** applies independently to the write and to the audit.

## Success, refusal, and failure boundaries

| Boundary | Expected result and side effects |
| --- | --- |
| Unauthenticated, malformed, missing/invalid key or content, forbidden project/target field | Safe preflight rejection; zero model/delegate/audit/Task/Execution/Memory/mapping delta. |
| Model unavailable, timeout, malformed output, wrong route, or proposed arguments | Existing distinct routing failure after durable audit reservation; no `save_memory()` call or new Memory/Task/Execution/M4 mapping. |
| Valid `no_action` | HTTP 200 routing `no_action`; one M12 audit row when final commit succeeds, zero Capability execution and write mapping. |
| Audit reservation or pre-delegate update failure/unknown acknowledgement | Safe M12 audit error; no delegate call or write, and only the last provable audit stage may be claimed. |
| Token revoked before or during delegate authorization | No Memory write; preserve the authoritative safe denial and any M1 pre-Task rejection record actually created. |
| Verified first write, keyed replay, conflict, pending, definite rollback, or `WRITE_OUTCOME_UNKNOWN` | Preserve the exact M1/M4 result and any original IDs. M12 audit records only the verified observation and correlation; no fallback or automatic retry. |
| Final audit failure after returned delegate result | Preserve that result, including a success or uncertainty, and mark only `routing.audit_status=unconfirmed`. |
| HTTP response lost | Neither absence of a client-visible `router_id` nor a nonterminal audit row proves write failure. The caller may explicitly inspect/replay through M4 using the retained original key and canonical body. |

## Automated validation matrix for implementation

- Existing requests without `memory_save`: unchanged M11/M12 read-only routes, preflight, `no_action`, audit status, and M1–M12 regression.
- Unauthenticated and invalid JSON/duplicate keys/extra fields: no model, delegate, or audit. Missing, duplicate, malformed key; missing, empty, oversized, or wrong-type content; forbidden scope, owner, or project argument: safe preflight rejection.
- Model input contains only the routing question and payload-present marker, never the separately supplied content or credentials. The strict M13 proposal accepts only `memory.save`/`no_action` and rejects all arguments, foreign routes, and malformed JSON. Actual Ollama opt-in checks a clear Korean and English explicit-save request and a `no_action` control; model selection quality is reported separately from write correctness.
- Valid `no_action` creates only the routing audit. On first verified success, exactly one selected internal `save_memory()` call creates its existing one Task, Execution, Memory, and M4 mapping; the router creates none. Verify owner is the authenticated user and the stored value is exactly M1's normalized `memory_save.content`, never question-derived.
- Same actor/key/canonical body replay returns original IDs without duplicate Memory/Task/Execution; a changed content under the same key conflicts; a different key may intentionally create another Memory. Concurrent same-key requests remain serialized by M4. A replay that the model routes elsewhere is not treated as a router-level guarantee.
- Revoked token at pre-delegate and inside `save_memory()`, definite DB rollback, running original, final write-commit acknowledgement unknown, response loss, and read-only M5 triage preserve their distinct contracts. No automatic retry, fallback, or guessed `running → failed` transition.
- Audit reservation, route-validation, dispatch-prepared, and final-observation definite failures/unknown acknowledgements: no delegate before a confirmed preparation; a final audit failure cannot rewrite a returned M1/M4 result. Verify `WRITE_OUTCOME_UNKNOWN` and `pending` are not labeled successful; M4 replay IDs are verified, while a pre-Task rejection never fabricates Task/Execution audit IDs.
- Inspect audit columns and serialized responses for absence of question, prompt, raw model output, Memory content, idempotency key/digest, token, password, answer, and path. Confirm no parent Task or generic dispatcher was introduced.

## Manual E2E plan after implementation

Use a separate synthetic user/token and a unique public test Memory, never an existing personal Memory. First confirm the Compose PostgreSQL baseline, private row fingerprints, named volume, local-only dedicated Ollama, and an empty M13 test-owned set. Capture the exact request body and one client key without printing credentials. Send one explicit user-scope routed save; verify the routing choice, original M1 result, exact stored synthetic content, one M4 mapping, one M1 Task/Execution, and a separately correlated M12 audit row. Make a deliberate same-key/same-body replay only after the first response is captured, to verify original IDs and no second Memory; do not perform an automatic retry on unexpected results. A `no_action` control and one safe preflight failure can verify zero write delta.

Use read-only DB checks to verify audit-to-execution ownership and to distinguish the current router ID from the original M4 request and Task IDs. After server shutdown and exact ownership checks, remove **only** synthetic user-owned records and confirm counts/private fingerprints return to their baseline. Do not delete existing users, Memories, Tasks, Executions, audit history, or Docker volumes. Record automated and manual results separately in a future M13 validation document; this document makes no claim that either has run.

## Explicit exclusions and documentation alignment

No model-derived Memory payload, project-scope write, Memory suppression/delete/edit/restore, automatic Memory extraction, multi-step planning, parent Task, generic capability registry, common invocation kernel, automatic retry/fallback/recovery, or router-level replay guarantee is included. M11/M12 historical read-only validation remains historical fact. No new Accepted DDR is required for this bounded branch if its explicit-input, permission, side-effect, and uncertainty rules hold; any later model-authored write or broader approval policy needs separate review against DDR-001, DDR-002, DDR-003, and DDR-006.
